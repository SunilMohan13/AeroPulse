# AeroPulse Source Likelihood — AI/ML Improvement & Productionization Plan

## 1. Executive Summary

I reviewed the three notebooks:

- `01_source_phase1_import_evidence_dataset.ipynb`
- `02_source_phase2_weak_labels_and_features.ipynb`
- `03_source_phase3_calibrated_classifier.ipynb`

The current implementation is a **good weak-supervision MVP**, but it should not yet be treated as a production source-attribution model.

The strongest aspects are:

- explicit separation between evidence collection and model training
- explicit scientific caveat that labels are likelihoods rather than proven causality
- train-only threshold fitting in Phase 3
- explicit exclusion of label-rule inputs from model features
- chronological and spatial evaluation
- probability calibration
- per-class metrics rather than relying on accuracy

The biggest architectural issue is more fundamental:

> The current system is called an independent likelihood / OvR system, but the actual weak-label function produces a single mutually exclusive `source_label` because later rules overwrite earlier labels.

For example, the labeler initializes every row as `mixed_unknown` and then successively assigns:

```text
dust
industrial
regional_transport
traffic
biomass_burning
```

Therefore a row that has both fire evidence and regional transport evidence ultimately receives only `biomass_burning`.

That means the current implementation is **not genuinely modelling independent source likelihoods**. It is modelling a single class generated by a priority-based heuristic.

For AeroPulse, I recommend evolving this into a **multi-label weak-supervision + calibrated likelihood architecture**:

```text
Evidence Sources
      │
      ├── Fire / FRP
      ├── NO2 / CO / SO2 / O3
      ├── PM2.5 temporal behaviour
      ├── Weather
      ├── Wind / transport
      ├── Dust indicators
      └── Spatial neighbours
              │
              ▼
       Evidence Feature Store
              │
              ▼
      Weak Labeling Functions
              │
              ▼
       Multi-label Targets
              │
              ▼
    Weak-supervision aggregation
              │
              ▼
       ML source classifiers
              │
              ▼
       Probability calibration
              │
              ▼
       Temporal + spatial validation
              │
              ▼
       Source likelihood API
              │
              ▼
        AeroPulse UI / Alert
```

## 2.1 Phase 1 — Evidence Dataset

The current Phase 1:

- imports the PM2.5 canonical/event-aware dataset
- validates required columns
- optionally retrieves OpenAQ co-pollutants
- caches co-pollutant results by `location_id`
- creates an evidence table
- stores a dataset fingerprint and manifest

The required inputs currently include:

```text
timestamp_utc
location_id
lat
lon
pm25
temperature_2m
relative_humidity_2m
wind_speed_10m
```

Optional pollutants include:

```text
NO2
CO
SO2
O3
PM10
```

The notebook correctly keeps co-pollutant collection optional and explicitly describes the data as evidence rather than attribution ground truth.

### What is good

The cache/resume behavior is useful for API-driven data acquisition, and the manifest/fingerprint is a good reproducibility foundation.

### Main gaps

The current evidence dataset does not sufficiently capture:

```text
data provenance
measurement quality
observation latency
source availability
forecast-vs-observed status
spatial uncertainty
temporal coverage
```

These become important when the source likelihood model is used operationally.

# 3. Phase 2 — Weak Labels and Evidence Features

The current notebook creates:

```text
hour
is_weekend
season
stagnation_flag
fire_active_flag
no2_pm25_ratio
```

and uses a heuristic weak-label function for:

```text
biomass_burning
industrial
traffic
dust
regional_transport
mixed_unknown
```

The current rule definitions are explicitly heuristic.

This is the correct conceptual approach for an initial weak-supervision system.

However, the current rule engine has a major limitation.

## 3.1 Current label overwrite behavior

The current sequence is effectively:

```text
mixed_unknown
      ↓
dust
      ↓
industrial
      ↓
regional_transport
      ↓
traffic
      ↓
biomass_burning
```

Later assignments overwrite earlier assignments.

Therefore:

```text
fire + strong wind + high PM2.5
```

does not produce:

```text
biomass_burning = high
regional_transport = high
```

It produces only:

```text
biomass_burning
```

This is inconsistent with the stated objective of independent source likelihoods.

---

# 4. Critical Architecture Change — Move to True Multi-Label Source Likelihood

Instead of:

```text
source_label = one class
```

create:

```text
biomass_burning_score
industrial_score
traffic_score
dust_score
regional_transport_score
```

and potentially:

```text
mixed_unknown_score
```

Example:

```json
{
  "biomass_burning": 0.92,
  "regional_transport": 0.81,
  "dust": 0.12,
  "industrial": 0.08,
  "traffic": 0.21
}
```

This is much more scientifically aligned with atmospheric transport.

A pollution episode can legitimately have multiple contributing mechanisms.

---

# 5. Replace Priority Rules With Labeling Functions

Instead of one large function:

```python
weak_source_labels(...)
```

create independent labeling functions.

Example:

```text
LF_FIRE
LF_TRAFFIC_NO2
LF_TRAFFIC_DIURNAL
LF_DUST_METEOROLOGY
LF_REGIONAL_TRANSPORT
LF_STAGNATION
LF_INDUSTRIAL
LF_BACKGROUND
```

Each function should produce:

```text
+1 = supports source
 0 = abstain
-1 = contradicts source
```

Example:

```text
LF_FIRE:

fire evidence high + PM2.5 elevated
→ +1

fire evidence absent
→ 0

```

Traffic:

```text
NO2/PM2.5 elevated
+
morning rush hour
+
weekday
→ +1
```

Dust:

```text
high wind
+
low humidity
+
pre-monsoon
+
high PM
→ +1
```

Regional transport:

```text
strong wind
+
upwind PM elevated
+
consistent transport direction
→ +1
```

This creates a much stronger weak-supervision framework.

---

# 6. Add Labeling Function Confidence

Every labeling function should have a reliability weight.

Example:

```yaml
labeling_functions:
  fire_frp:
    source: biomass_burning
    reliability: 0.95

  no2_morning:
    source: traffic
    reliability: 0.75

  stagnation_weekend:
    source: industrial
    reliability: 0.45

  wind_pm:
    source: regional_transport
    reliability: 0.60
```

This is preferable to treating every heuristic as equally reliable.

---

# 7. Add Conflict Detection

The system should explicitly identify conflicting evidence.

Example:

```text
fire evidence       = strong
traffic evidence    = strong
dust evidence       = moderate
regional transport  = strong
```

Instead of forcing one class, produce:

```text
primary_candidate
secondary_candidates
conflict_score
```

Example:

```json
{
  "primary": "biomass_burning",
  "secondary": [
    "regional_transport",
    "traffic"
  ],
  "conflict_score": 0.72
}
```

This makes the output more scientifically honest.

---

# 8. Do Not Use `mixed_unknown` as an Ordinary Class

`mixed_unknown` is fundamentally different from the other source hypotheses.

It means:

```text
available evidence is insufficient
or
multiple sources cannot be separated
```

It should therefore be treated as:

```text
uncertainty / unknown state
```

rather than simply another classification class.

Recommended output:

```text
source likelihoods
+
attribution confidence
+
unknown probability
```

# 27. Important Evaluation Issue

The current model evaluates against **weak labels generated by the same heuristic system**.

Therefore:

```text
high F1
```

does not mean:

```text
high scientific source-attribution accuracy
```

It means:

```text
the ML model reproduces the weak-labeling system
```

This distinction should be explicit in every report.

# 45. Production Fallback

The source likelihood service must degrade gracefully.

If fire data is unavailable:

```text
biomass likelihood → low-confidence / unavailable
```

If NO2 is unavailable:

```text
traffic likelihood → lower confidence
```

If weather is unavailable:

```text
transport/dust confidence → reduced
```

Never convert missing evidence into negative evidence.

```text

        ↓

        ↓
AeroPulse Source Likelihood API
```

## Most important recommendation

The most important change is **not changing Logistic Regression to a more sophisticated model**.

The highest-value change is fixing the target definition.

The current heuristic produces a single priority-selected class even though the architecture claims to provide independent source likelihoods. Before improving the classifier, change the labels to genuine multi-label probabilistic source hypotheses.

Once that is done, improve the evidence representation—especially **upwind fire influence, wind-aware regional transport, pollutant temporal signatures, PM10/PM2.5 dust evidence, station context and evidence availability**.

Then introduce a small human-reviewed gold dataset. This will provide the first meaningful measurement of whether AeroPulse is learning actual source signals rather than simply reproducing its own heuristics.

That sequence will give AeroPulse a much stronger and scientifically defensible source-likelihood capability without prematurely introducing complex deep-learning models.
